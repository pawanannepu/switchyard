# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Local storage for the engine. Projects, tasks, workspaces, runs and a journal of every change now live in `switchyard.db` (SQLite in WAL mode) inside the data dir, and each run's raw terminal output goes to its own file, `runs/<run_id>.log`. The data dir and its folders are `0700` and every file is `0600`, so only you can read them. (see spec 0002)
- Nothing you saw is lost on a hard kill. Run output is written to its log file before any client receives it, and a run's status change is committed before the `run.status` notification goes out. After a restart, runs that were still live are marked `lost`, and leftover files that belong to no run are cleaned up. (see spec 0002)
- `event.since` method: read the change journal from a cursor, filtered by project, task, workspace or run, 200 events per page by default (500 at most), with `next_cursor` and `has_more`.
- `run.log_read` method: read a run's saved output by byte offset, during the run or after it ends, up to 256 KiB per call.
- `run.status` notification, sent to every connected client after `session.hello`, with the id of the journal event it came from.
- `storage.status` notification, plus an optional `storage` field on `engine.info` that reports `ok`, `degraded_writes`, `newer_schema`, `corrupt` or `unavailable`.
- Safe recovery from a broken database. If the database is corrupt, from a newer version, or can't be opened, the engine still starts and explains why, and every method except the stable ones and `storage.recover` returns `StorageUnavailable`. `storage.recover` then restores the newest backup that passes a check, or starts fresh. It moves the bad files aside under a `.bad-<time>` name and never deletes them.
- Automatic backups in `backups/`: one before each schema migration and one a day, checked before they are kept. The 3 newest are kept.
- The engine keeps working when the disk is full or a write fails. Agents keep running and their output keeps streaming live. Database writes wait in an in memory queue and are retried every 5 seconds, and storage status shows `degraded_writes` until they succeed.
- A size cap on run logs, set by the `storage.log_cap_bytes` setting (5 GiB by default). When the cap is passed, the engine removes logs of ended runs in archived tasks only, oldest first. Logs of active tasks and live runs are never removed.
- New protocol error codes: `RunLogUnavailable` (`-32043`), `StorageUnavailable` (`-32050`), `StorageRecoverNotNeeded` (`-32051`) and `BackupMissing` (`-32052`).
- One interface every coding agent plugs into, in the new `sy-adapter-api` crate (`CONTRACT_VERSION = 1`). An adapter is a pure translator: it describes how to detect and launch its agent, and its per run decoder turns hooks and terminal output into status, approvals, events and a session id. Adapters never spawn processes, open files or touch the network. The engine does all of that, so adding an agent means one new crate and one registration line. (see spec 0003)
- Agents run their real interactive terminal app in a PTY owned by the engine, so you see and type into exactly what you would in your own terminal. The output goes through the same run log as before, so nothing you saw is lost on a hard kill. Each run gets its own launch dir under `<data dir>/agent-runtime/`, which is removed when the run ends. The engine never writes to your worktree or to an agent's global config.
- `sy-signal`, a small helper that an agent's hooks run to report to the engine over `engine.sock` with a per run token, using the new `signal.hook` method. If the engine can't be reached, it falls back to the agent's own prompt and never auto approves. It ships in the app bundle next to `switchyardd` and is signed with it.
- Live run status. A run moves to `running`, shows `waiting_input` while it has a pending approval or the agent is waiting for you, and ends `finished` or `failed` with its exit code. Agent events (messages, commands run, files changed) and the agent's session id are recorded too.
- Approvals. Permission requests from an agent are saved in a new `approval` table (migration 2) and sent as `approval.requested`. You can list them with `approval.list` (filtered by status and run, keyset paged) and answer them with `approval.respond`. The first answer wins any race with a stop, the run ending, or an answer typed in the terminal, and every change is sent as `approval.decided`. Pending approvals become `cancelled` when their run ends and `expired` when the engine restarts.
- `run.stop` method: sends the agent its graceful stop input, then SIGHUP, then SIGKILL. Engine shutdown stops every live run this way and takes at most about 8 seconds.
- Agent detection without reading your login tokens. `agent.list` shows every registered agent with its capabilities and whether it is installed and signed in, and `agent.detect` checks again. The Claude adapter detects `claude` through `claude --version` (sign in always shows as unknown). It cannot launch runs yet.
- The engine captures your login shell environment at start, so agents find the same `PATH` you have in your terminal. `env.refresh` captures it again and reruns detection, and `engine.info` gains an optional `login_env` field that says `ok` or `fallback`.
- A scripted fake agent for tests: `sy-fake-agent` runs JSON steps through a real PTY and reports through `sy-signal`, exactly like a real agent. It exists only in `devtools` builds, and you start it with the new `dev.agent_run` method.
- New protocol error codes: `NotAllowedForClient` (`-32002`), `RunNotLive` (`-32044`), `AgentNotFound` (`-32060`), `AgentLaunchUnsupported` (`-32061`), `ApprovalNotFound` (`-32070`), `ApprovalNotPending` (`-32071`), `SignalTokenUnknown` (`-32080`), `SignalPayloadTooLarge` (`-32081`) and `SignalRateLimited` (`-32082`).
- Run limits, so an agent that hangs, loops or floods its terminal is stopped on its own. Each run has an idle limit (no output and no hook call while `starting` or `running`, 30 minutes by default), an active time limit (time spent `starting` or `running`, 4 hours by default) and an output limit (512 MiB by default). You set them with the `limits.run_idle_ms`, `limits.run_active_ms` and `limits.run_output_bytes` settings, globally or per project. A project setting wins over the global one, and `0` turns a limit off. An invalid value is skipped with one warning in the engine log. A run keeps the limits it started with, so a change applies to the next run. The clocks don't move while your Mac sleeps, so waking it up never trips a limit. (see spec 0004)
- When a run hits a limit, the engine journals a `run_limit_exceeded` event (`limit` is `idle`, `time` or `output`, with its `threshold` and the `observed` value). Then it stops the run the same way `run.stop` does. Held approvals get a deny with `run stopped: <limit> limit` and become `cancelled`. The run ends `failed` with the new end reason `limit_exceeded`.
- Nothing an agent started keeps running after its run ends. While runs are live, the engine scans the process table every 2 seconds and records each agent's processes in a new `run_process` table (migration 3), up to 256 per run. When a run ends, for any reason, the engine sweeps its leftovers: SIGTERM, up to 3 seconds, then SIGKILL. This includes processes that left the agent's process group. Before signalling a process, the engine checks it still has the recorded start time and belongs to you, so a reused pid is never signalled. Only the short executable name is stored, never arguments or environment. The run's `pid_started_at` is now recorded at spawn. (see spec 0004)
- Cleanup after an engine crash. At start, the engine stops any processes the previous engine left behind, from the `run_process` rows, and deletes their rows. It accepts connections while this runs in the background.
- Fault isolation. A panic while the engine supervises one run (its driver, or its terminal reader, writer or exit waiter) fails only that run, with the new end reason `supervisor_error`. Its held hooks fall back to the agent's own prompt, its pending approvals become `cancelled`, and its processes are swept. Other runs, the socket and the engine keep running. The engine log records the panic's location with the run id.
- The engine raises its open file limit to 4096 at start (or the system's hard limit, if lower), so many live runs don't run out of file descriptors. Agents inherit it.
- New fake agent steps for tests, in `devtools` builds only: `spawn` (start a child that blocks forever, optionally `detach`ed from the agent's group or ignoring SIGHUP or SIGTERM), `ignore_sigterm` and `panic_decoder`. `dev.agent_run` gains an optional `limits` param (`idle_ms`, `active_ms`, `output_bytes`) that wins over every setting, and it refuses values above 2^53.

### Changed
- The error code range `-32050` to `-32059` is now the storage block. It was reserved before.
- The error codes `-32060` to `-32089` are now split into blocks for agents (`-32060` to `-32069`), approvals (`-32070` to `-32079`) and signals (`-32080` to `-32089`). They were reserved before.
- The Load check screen and the socket tests now drive the fake agent through `dev.agent_run` with a `flood` script, in place of synthetic runs.
- `pnpm boundaries:check` now fails if any adapter crate uses file, process, network or environment APIs. `pnpm release:check` now also checks that `sy-signal` is signed, and fails if the bundle contains `sy-fake-agent` or the bundled engine lists the fake agent.
- Engine shutdown now also waits for every run's leftover sweep, so it takes at most about 13 seconds (it was about 8). (see spec 0004)
- Release builds now use `panic = "unwind"` in place of `panic = "abort"`, so a panic in one run's supervision can't stop the whole engine. The binary is somewhat bigger.
- In `devtools` builds, `dev.synthetic_run` now creates real fixture rows (a project, a task, and a workspace plus run for each synthetic run) and saves their output, and it returns `task_id` and `workspace_ids` too. `dev.stop_runs` marks those runs `stopped`.

### Removed
- The `dev.synthetic_run` and `dev.stop_runs` devtools methods. Use `dev.agent_run` with the fake agent and `run.stop` instead.
