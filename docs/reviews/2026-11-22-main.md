## Summary

This change builds the data model from spec 0002. It adds typed ids, the domain model and status machine, the `Store` and `RunLog` ports, a SQLite store on its own thread, migrations, backups, degraded open and `storage.recover`, a degraded write queue, startup recovery, log cap trimming, and the new protocol methods. The quality is high. The architecture follows the crate table, persist before broadcast is built and tested, and the checks I ran are green: `cargo clippy` with `-D warnings`, `cargo test --workspace` (and `cargo test -p sy-daemon --features devtools`, 38 tests), `cargo deny`, `pnpm boundaries:check` and `pnpm protocol:check`. The headline problems are that the root `package.json` lost its aggregate scripts, which breaks CI and the commands this same change documents in AGENTS.md, and that a bad input value can flip the whole engine into `degraded_writes`.

## Blockers

### 🔴 Root `package.json` lost its `typecheck`, `lint`, `format`, `format:check`, `test`, `test:e2e` and `prepare` scripts, `package.json:7`
**Problem**: The diff deletes seven scripts from the root `scripts` block and adds `vitest` to the root devDependencies. After this change `pnpm typecheck` fails with `Command "typecheck" not found`. The scripts still exist in `apps/desktop/package.json` and `packages/protocol-ts/package.json`, so only the root aggregates are gone. The same diff edits AGENTS.md to tell people to run `pnpm test`, `pnpm test:e2e`, `pnpm typecheck`, `pnpm lint` and `pnpm format:check`.
**Why it matters**: `.github/workflows/ci.yml` calls `pnpm format:check`, `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm test:e2e`, so CI would fail on this change. The testing gate in AGENTS.md ("isn't done until they pass") cannot be run from the root. Dropping `prepare` also stops `lefthook install` from running after `pnpm install`, so the pre-commit hook silently stops being installed. It also looks unrelated to the data model, so it is probably an accident (a stale file or a bad merge).
**Suggested fix**: Restore the seven scripts exactly as they are in HEAD. Then decide separately whether the root really needs a `vitest` devDependency. The lockfile already lists it, but nothing at the root runs it.

## Major

### 🟠 Input and validation errors are classed as storage failures and can degrade the engine, `crates/sy-infra/src/storage/sqlite.rs:84` and `crates/sy-core/src/write_queue.rs:141`
**Problem**: `map_err` turns every constraint violation it does not recognise (a `CHECK`, `NOT NULL`, a primary key clash, `json_valid` on `agent_options`) into `StoreError::Io("constraint failed: ...")`. `corrupt()` also returns `Io`. `QueuedStore::is_storage_failure` treats every `Io` as a failure that queueing can wait out. So a caller error, for example `NewWorkspace.agent_options` that is not valid JSON (it is a raw `String`), makes `unqueued` call `degrade`. Storage then reports `degraded_writes`, every create fails with `Full`, and a `storage.status` notification goes to all clients. A queued command that fails on replay with such an `Io` also makes `retry` return false forever, so it blocks the head of the queue and storage never recovers.
**Why it matters**: One bad request from a client, or a future feature 8 bug, can put the whole engine into a degraded mode that also hides the real cause. The spec says only disk full or I/O errors degrade. The test `a_refusal_while_ok_should_pass_through_and_never_degrade` uses a test double, so it does not cover the real SQLite error mapping.
**Suggested fix**: Add a distinct `StoreError` variant for constraint or data errors that are not a mapped unique index (and one for unreadable stored data), and keep both out of `is_storage_failure`. Type `agent_options` as a JSON value in core so bad JSON cannot reach the insert. Add an integration test that a CHECK violation on the real store returns that variant and leaves health `ok`. Make `retry` drop a replayed command that fails for a non storage reason, as it already does for the refusals it knows.

## Minor

### 🟡 A failure in startup recovery stops the engine from starting, `crates/sy-daemon/src/server.rs:73`
**Problem**: `recover_at_startup(...).await.context(...)?` returns an error out of `run()`, so the engine exits non zero. The write calls in recovery go through `unqueued`, so a full disk at start makes `mark_live_runs_lost` fail with `Full`.
**Why it matters**: Full disk is the exact case this feature is meant to survive. Starting with a full disk makes the engine exit and the app cannot connect to tell the user why. AC-3 asks for degraded mode, not exit, when a start step fails.
**Suggested fix**: Log the failure and carry on. Either leave storage in `degraded_writes` and retry recovery once writes return (the retry loop already wakes the log cap), or report the failure through `engine.info.storage` as `unavailable`.

### 🟡 A failed `storage.recover` can leave the database set aside with nothing restored, `crates/sy-daemon/src/storage.rs:212`
**Problem**: `set_aside` renames the db, `-wal`, `-shm` and `runs/` first, then `restore` copies the backup. If the copy fails (or the process dies between the two), the engine still reports the old failed state, but `switchyard.db` no longer exists.
**Why it matters**: The next engine start opens a brand new empty database without a word, and the history is only in `*.bad-*` files. Nothing is deleted, but the user is not told.
**Suggested fix**: If `restore` fails after `set_aside`, create the empty database path deliberately and report it (or move the set aside files back). At the least write a clear error and log line naming the `.bad-*` files.

### 🟡 Timestamps of queued changes are the replay time, `crates/sy-core/src/write_queue.rs:507`
**Problem**: A queued `transition_run` is stored as `(actor, run, change)` with no time. On replay `Run::transition` uses the clock at replay, so `ended_at`, `started_at` and the event `at` can be minutes late. The `run.status` notice sent at queue time carries the earlier `at`, so the live notification and the journal disagree.
**Why it matters**: Feature 27 computes durations from these fields, and an event stored as happening after the next event that really came later breaks ordering by `at`.
**Suggested fix**: Capture `now` when the command is queued and pass it into the replayed transition (and into the event), so the stored time matches what clients were told.

### 🟡 Two spec test scenarios are covered only in part, `crates/sy-daemon/tests/engine.rs:1725` and `:696`
**Problem**: AC-17 asks for a prompt containing a marker string. The marker test sends the marker through run output and input, but the dev fixture task prompt is `""`, so a prompt is never written and never checked. The umask scenario ("a child the engine spawns sees the umask it started with") is a source scan for the text `umask(`, not a behaviour check.
**Why it matters**: The prompt is the one user text the store holds and journals (`task_created` payload carries the title). The scans prove nothing about the real behaviour if the code changes shape.
**Suggested fix**: Add a store level test that creates a task with a marker prompt and title and asserts it never appears in `engine.log` with tracing at debug level. Keep the scan but add a note that it stands in until feature 5 spawns children.

## Nits

- ⚪ `crates/sy-infra/src/storage/sqlite.rs:72`, mapping a unique violation by parsing SQLite's "UNIQUE constraint failed: cols" text is fragile if two indexes ever share a column list or the text changes in a SQLite upgrade. The live schema test helps; consider adding a comment that a new unique index must have a distinct column list.
- ⚪ `crates/sy-daemon/src/storage.rs:169`, `Storage::info()` lists the `backups/` directory on every call, and it runs on async request handlers and on every `storage.status` broadcast. Cache the latest backup name when a backup is written.
- ⚪ `crates/sy-daemon/src/server.rs:64`, `Storage::open` (integrity check, `VACUUM INTO`, migrations) blocks a runtime thread. Acceptable at startup, but wrap it in `spawn_blocking` like `recover` does, so a slow check does not stall the signal listener.
- ⚪ `crates/sy-core/src/write_queue.rs:252`, `retry` holds the state mutex across the whole replay (up to 10000 commands), so new `transition_run` and `get_run` calls wait for it. Fine for now, worth a comment.
- ⚪ `test-preferences.json`, a new untracked tool config at the repo root. Decide whether to commit it or ignore it.

## Strengths

- Persist before broadcast is built with care: the per run flush lock, the ring filled only after the append, the `pwrite` at an exact offset, and a unit test that races `remove()` against the flusher.
- The open sequence is thoughtful: `NO_CKPT_ON_CLOSE` keeps a damaged file and its WAL untouched until it passes its checks, and backups go through a `.tmp`, `quick_check` and rename.
- Entity rules live in `sy-core` and are unit tested without infrastructure (status machine, id parsing, log reconcile, display status). `StoreError` and `OpenError` are clean `thiserror` enums, and the port boundary holds (`pnpm boundaries:check` passes).
- The schema matches the spec closely (STRICT tables, named partial unique indexes, composite FK that copies `project_id`), and `workspace.project_id` is copied inside the insert.
- Good use of real systems in tests: real SQLite files, real sockets, `kill -9`, an actual `rebuild` migration that keeps child rows, and fault injection that is compiled only into devtools builds.
- Every `pub` item has a doc comment, there is no `unsafe`, no `unwrap` outside tests, and the generated protocol files are in sync.
