## Summary

This builds spec 0003: the pure `sy-adapter-api` contract, the per-run driver task in `sy-core/src/agents/`, the real PTY, probe, login-env and launch-dir adapters in `sy-infra`, `sy-signal`, the fake agent and adapter, the approvals table, store methods and protocol methods, detection, and the release gates. The architecture follows the spec closely. Dependency direction is clean, there is no `unsafe`, every decoder call and approval change goes through the one driver task, and the first-change-wins rule is enforced in SQL as well as in memory. `cargo clippy --workspace --all-targets --all-features -D warnings`, `cargo test --workspace`, `pnpm boundaries:check`, `pnpm protocol:check` and the TS typecheck all pass here. One real ordering race should be fixed before merge, and a handful of minors are listed below.

## Major

### 🟠 Approval notifications can be overtaken by later `run.status` events, `crates/sy-daemon/src/engine.rs:247`
**Problem**: `spawn_broadcaster` has three channels in a `biased` select: committed events first, then storage notices, then approval notices. The driver commits an approval row (its event goes into the committed-events channel) and then sends the `ApprovalNotice` on a separate unbounded channel. The same driver then commits the next status transition, whose event goes into the committed-events channel again. If the broadcaster has not yet polled between those two points, the biased select drains every queued committed event, including the later `run.status`, before it looks at the approvals channel.
**Why it matters**: AC-17 and the "Run end order" scenario require `approval.decided` (cancelled) to arrive before the terminal `run.status`. AC-9/AC-10 imply `approval.requested` precedes the `waiting_input` `run.status` it causes. The doc comment on `spawn_broadcaster` claims ordering ("a notice is always sent after the commits before it"), but that only holds for earlier commits, not later ones. Under load (12 runs, slow clients, a descheduled broadcaster task) clients will see the order inverted. The socket tests pass only because the broadcaster usually wins the race, so they can flake.
**Suggested fix**: Put approval notices on the same ordered path as committed events. For example, have the driver send them down one channel that carries both event and notice items in the order the driver produced them. Or keep one channel and make the store's committed event the trigger for the approval line. Then add a test that delays the broadcaster, for example by holding a slow subscriber, and asserts the order.

## Minor

### 🟡 Boundaries purity scan is line by line and comment stripping eats string contents, `scripts/check-boundaries.mjs:116-137`
**Problem**: `forbiddenApi` is tested against one line at a time. The grouped-import patterns need the closing `}` on the same line, so the rustfmt form `use std::{` followed by `fs,` on the next line is not caught. `stripComments` also removes everything after `//` even inside a string literal, for example `"https://x"; std::fs::read(..)`.
**Why it matters**: AC-2's "token rule holds by check" is the headline security invariant, and this script is the only mechanical enforcement. Long multi-line `use std::{...}` blocks are the normal rustfmt output as adapters grow (feature 8 and later).
**Suggested fix**: Scan the whole file text, not per line, and join or tokenize `use` statements (or parse with a simple brace-aware pass). Strip comments only outside string literals. Add a self-test fixture for the multi-line and the string cases.

### 🟡 A failed `decide_approval` orphans the row as `pending`, `crates/sy-core/src/agents/driver.rs:358` and `:632`
**Problem**: `decide` removes the entry from `self.pending` before the store call, even when it fails with something other than "not pending". `end()` only calls `cancel_pending_approvals` when `self.pending` is non-empty. A row whose decide failed (storage error) stays `pending` in the database after the run ends. `approval.list` shows it, `approval.respond` answers `ApprovalNotPending`, and nothing clears it until the next engine start.
**Suggested fix**: Call `cancel_pending_approvals` unconditionally at the end of the run, since it is a cheap indexed query. Or keep failed entries in a "needs cancel" set.

### 🟡 `sy-signal` has no connect or hello timeout, `crates/sy-signal/src/main.rs:111`
**Problem**: `relay` waits on connect and hello forever. Only the `signal.hook` reply is meant to wait long.
**Why it matters**: `status`, `session` and `event` hooks run on the agent's hot path. A wedged but listening engine (for example stuck on a store call) stalls every hook, and so the agent, until the agent's own timeout. The spec says an unreachable engine must fall back.
**Suggested fix**: Bound connect plus hello (about 2 s) and fall back on expiry. Leave the reply wait unbounded.

### 🟡 Starting a run is not tied to shutdown, `crates/sy-core/src/agents/mod.rs:500` and `:862`
**Problem**: `stop_all` snapshots `live` once and then waits for the live-run count to reach 0. A `start` already in flight (for example a `dev.agent_run` with `count` up to 32, each start awaiting the login capture and a spawn) can register runs after the snapshot. Those runs never get a `Stop`, and `stop_all` waits for them to end on their own. A `hang` script would block shutdown indefinitely.
**Why it matters**: Dev-only today, but feature 8 reuses `AgentRuns::start`.
**Suggested fix**: Give `AgentRuns` a "stopping" flag set at the start of `stop_all`. `start` refuses (or immediately stops) new runs once it is set. Loop `stop_all` until the set is empty.

### 🟡 `start` can leave a `queued` run with no driver, `crates/sy-core/src/agents/mod.rs:522`
**Problem**: If `hub.create_run` fails (`StartError::Hub`) after `create_run` succeeded, the run row stays `queued` forever, with no driver and nothing to end it. `run.stop` can still end it, but nothing does automatically.
**Suggested fix**: End it `failed` with `spawn_failed`, as the other launch failures do, or create the hub entry before the row.

### 🟡 New approvals are accepted while a stop is in progress, `crates/sy-core/src/agents/driver.rs:317`
**Problem**: `request` only refuses once `ending` is true. After `begin_stop` has denied the held hooks, a hook arriving during the grace (up to 10 s) or the SIGHUP wait is held again, until the exit or the final end sequence. A run being stopped can also show a fresh pending approval in the inbox.
**Suggested fix**: Treat `stop_requested` like `ending` in `request`, so a late hook gets the fallback or an immediate deny with "run stopped".

### 🟡 A panicking detection pass wedges all later passes, `crates/sy-core/src/agents/detect.rs:111`
**Problem**: `in_flight` is cleared after `pass().await` inside the spawned task. If `pass` panics (an adapter bug), the sender drops without sending `true` and `in_flight` stays `Some`. Every later `detect` or `env.refresh` joins the dead pass and no detection ever runs again.
**Suggested fix**: Clear the slot with a drop guard, or run `pass` under `catch_unwind`.

### 🟡 Degraded `list_approvals` overlay corrupts paging, `crates/sy-core/src/write_queue.rs:1007`
**Problem**: Queued decisions are overlaid on the database page and then filtered by status. `next` and `has_more` come from the pre-overlay page. Rows that were decided only in the queue are missing from a non-pending filter, and a page can come back short while `has_more` is true.
**Suggested fix**: Fine to document as a known degraded-mode limitation, or merge queued approvals into the result by (`requested_at`, `id`) before cutting the page.

### 🟡 Claude `launch` is never exercised, `crates/sy-adapters/claude/src/lib.rs:144`
**Problem**: `launch_should_be_unsupported_until_feature_8` only asserts `capabilities().launch` is false. AC-15 says `launch` returns `AdapterError::Unsupported`, which is untested.
**Suggested fix**: Call `launch` and assert the error variant.

## Strengths

- One driver task per run owns the decoder, approvals, token revocation and the AC-17 end order. Approval changes are decided there and also guarded by `WHERE status = 'pending'` in SQL, so first change wins holds at both levels.
- Process-group signalling is race-safe: `waitid(WNOWAIT)` sees the exit, then the reap and the "reaped" flag share one lock with `signal_group`. A reused pgid can never be hit.
- Pure adapters and the `allowed_program` and `agent_env` rules are small, pure and unit tested (absolute vs bare matching, `..` refusals, env composition).
- `detail_json` truncation, with a binary search over the escaped length so `raw` always fits 64 KiB, is correct and tested for quote, newline and multibyte inputs.
- Degraded-storage behaviour for approvals (never queue creates, queue decisions and cancels in order) is thought through and has its own integration test.
- The fake agent runs the production path (real PTY, `sy-signal`, socket). The release check now asserts no `fake`, no `sy-fake-agent` and a signed `sy-signal`.
