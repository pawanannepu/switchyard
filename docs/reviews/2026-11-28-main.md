## Summary
Implements spec 0004: run limits (idle, active, output) with monotonic clocks, a shared process tree scanner, a persisted `run_process` table, a per run monitor that sweeps leftovers after the run ends (main process held as an unreaped zombie), restart cleanup from a pre-accept snapshot, and per run panic isolation (`supervisor_error`). The core is carefully built: the pure parts (`supervise.rs`) are well factored and heavily unit tested, the signal-safety rules (start time, uid, pid 1, engine, unreaped group) are applied consistently, the layering rules hold (`pnpm boundaries:check` passes, `sysinfo` and `cfg(unix)` only in `sy-infra`), and the socket tests cover the spec's critical scenarios. I found no blockers and no majors. The findings are narrow races, one spec/implementation drift (AC-1 for an already-exited main), and a few robustness and hygiene points.

## Minor
### 🟡 AC-1 "exited main is still recorded" is not met by the real `ProcessTable`, `crates/sy-infra/src/agents/proc_table.rs:3-8` and `crates/sy-core/src/agents/mod.rs:858-865`
**Problem**: AC-1 (and the spec's pid_started_at test scenario) says a main process that already exited is still an unreaped zombie that still reports a start time, so it is recorded. The module comment of `proc_table.rs` documents the opposite for `sysinfo` on macOS: a fresh `System` reads a never seen zombie as absent, and `a_held_zombie_should_read_as_gone_and_never_be_signalled` asserts it. So an agent that dies within the ms between `spawn` and `record_main` (a failing launch is the realistic case) gets `pid_started_at = NULL` and no main `run_process` row. The core test passes only because its scripted double returns a start time for a zombie.
**Why it matters**: The consequence is small (the sweep still works: `Tracker::new(pid, None, ..)` falls back to the session rule, the zombie keeps the group reserved), but restart cleanup then has no main row for that run, `pid_started_at` is NULL where the spec promises it, and the spec and code now disagree.
**Suggested fix**: Either read the start time inside the spawn path before the child can be reaped by anything (for example from `portable-pty`/`proc_pidinfo` directly for the just spawned pid, which does answer for zombies), or amend AC-1 and the Critical test scenarios to say the main is untracked when it exited before the read, and add an infra test for that real behaviour.

### 🟡 A panic in the monitor or in `fault_end` leaks the run's live count, `crates/sy-core/src/agents/mod.rs:997-1011`
**Problem**: `finish()` (which removes the tracking entry and decrements `drivers`) runs only if `monitor` runs to the end. `fault_end`/`sweep` are the code that runs *after* something already went wrong, and nothing guards them (no catch, no drop guard). A panic there leaves `drivers` permanently above zero.
**Why it matters**: `stop_all` waits for `drivers == 0` and idle exit/drain wait on the same counter, so one such panic turns "fails only that run" into "the engine can never shut down or idle exit", and the scanner keeps scanning forever.
**Suggested fix**: Make `finish` a drop guard created at the top of `monitor` (or wrap the sweep and fault end in `catch_unwind`/`JoinHandle` and always call `finish`). Add a monitor unit test where the sweep panics.

### 🟡 The scanner can write a run's rows after its terminal transition, `crates/sy-core/src/agents/scanner.rs:68-90`
**Problem**: `observe` puts new keys in `tracker.tracked` and returns `insert`; the `is_closed` check happens under the lock, but `track_processes(...).await` runs after the lock is released. If the run's terminal transition and its sweep (whose step 6 deletes every key in `tracker.tracked()`) complete inside that await, the insert lands after the delete.
**Why it matters**: Violates the stated invariant "the scanner never writes for a run after its terminal transition" and leaves a stale row until the next engine start (harmless to safety, since a mismatch counts as gone, but the table is meant to be empty when nothing runs). The same shape exists for the degraded queue replaying `TrackMain` after the sweep's delete.
**Suggested fix**: Hold a per run async write lock (or an in flight counter the sweep waits on) across insert/delete writes so the sweep's step 6 runs after the scanner's last write; or have step 6 re-delete once after waiting out the in flight scan.

### 🟡 `start` can be cancelled after the agent was spawned, `crates/sy-core/src/agents/mod.rs:833-886` (called from `crates/sy-daemon/src/dev.rs:168`)
**Problem**: `launch` now awaits three store/blocking calls (`record_main`) after the spawn. If the caller's future is dropped there (connection task aborted at shutdown or on a client error path), the `PtyChild` is dropped (its `Drop` kills and reaps the group, good) but `drivers` was already incremented and `live`/`signals`/hub entries were inserted, so the run stays `starting` in the store and the live count never returns to zero. This class existed before, but spec 0004 widened the window.
**Why it matters**: Same shutdown/idle-exit hang as above, plus a run row stuck non terminal until the next start marks it `lost`.
**Suggested fix**: Do the post spawn bookkeeping inside the spawned monitor/driver path, or run `start`'s post `create_run` section in a detached task that always reaches `fail_start`/`drive`. Verify with a test that drops the `start` future after the spawn.

### 🟡 Panic hook discards the message and replaces the default hook, `crates/sy-daemon/src/main.rs:46-60`
**Problem**: `set_hook` logs only location, thread and run id and never calls the previous hook. This applies to every panic in the daemon, not only supervision ones, and nothing goes to stderr any more.
**Why it matters**: A panic in a non-run thread (storage worker, socket server) now leaves only a file:line in the log. If the log appender is the thing that failed, the panic leaves no trace at all.
**Suggested fix**: Keep the "no payload" rule for run scoped panics if that is the intent, but log a `&'static str` payload (never a formatted one), and chain to the previous hook so stderr still gets the default report for non run panics.

### 🟡 Release profile isolation test is missing, `crates/sy-daemon/tests/engine.rs:3726-3850`
**Problem**: The spec's Migration risk section and Critical test scenarios require the panic isolation test to also run under `cargo test --release -p sy-daemon` to prove `panic = "unwind"` in the shipped profile. The tests exist, but nothing wires or documents a release run (no CI step, no `#[cfg]` note, no `release:check` hook), and the AGENTS.md test commands don't mention it.
**Why it matters**: `panic = "unwind"` is the load bearing change for AC-11. If a later edit flips the profile back, only the daemon's startup log line warns.
**Suggested fix**: Add the release run to CI (or a `pnpm` script) and, since `cfg!(panic = "abort")` is known at compile time, add a cheap unit test asserting `!cfg!(panic = "abort")` for the profiles the engine ships in.

## Nits
- ⚪ `scripts/check-boundaries.mjs:26`, `sysinfo` is not in the `STORAGE` forbid list, so nothing stops `sy-core` from depending on it; spec 0004 says "sysinfo in sy-infra only" and that the allow lists are updated.
- ⚪ `crates/sy-core/src/agents/supervise.rs:434-482`, `observe` rechecks the main key once it is a zombie (it is not in `alive`), so the scanner can delete the main row between the exit and the terminal transition; the spec says the sweep removes it. Skip `main_key` in `recheck`.
- ⚪ `crates/sy-core/src/agents/supervise.rs:318-343`, `is_root` is a linear `contains` over up to 256 roots inside a chain walk, repeated per process, per run, per scan; use a `HashSet` and build `by_pid` once per scan instead of once per run.
- ⚪ `crates/sy-core/src/agents/mod.rs:960-963`, when `drive` fails after the main row was inserted, the process is killed but its row stays until the next start (no sweep runs).
- ⚪ `crates/sy-core/src/agents/mod.rs:448`, `bad_settings` is an unbounded set keyed by value text (including store error strings for the `"*"` project key); cap it.
- ⚪ `crates/sy-core/src/agents/fault.rs:98-104`, if the waiter thread itself panicked, `exited` is never set, so `fault_end` waits the full 5 s + 1 s before ending the run; the waiter's panic path could set `exited` (it knows the process state is unknown) or probe `process` directly.
- ⚪ `docs/specs/0004-agent-process-supervisor/index.md:118,308`, the spec says one `sysinfo::System` behind a mutex, the code builds a fresh `System` per scan/check (documented in `proc_table.rs`), and the open follow-up "does `sysinfo` report session ids on macOS" is answered (it calls `getsid`) but still unchecked.

## Strengths
- `supervise.rs` is a clean, pure, well tested core: monotonic clocks with the 2 s tick cap, `>=` checks in the spec's order, a `Tracker` that encodes the two scans rule, the cap, the closed flag and gone candidates, with many edge case tests (cycles, pid 1, reparenting, a main with no start time).
- Signal safety is layered correctly: per pid signals re-check start time, uid, pid 1 and the engine immediately before `kill`; group signals only while the main is unreaped (checked under the same lock as the reap); restart cleanup works strictly from the pre-accept snapshot and never signals a mismatched row.
- Fault isolation is thoughtful: `catch_unwind` at each thread boundary feeding `Control::SupervisorFault`, a monitor that finishes the end order for a panicked driver idempotently (including the "already terminal, only clean up and sweep" case), and a thread/task local run id for the panic hook.
- Good socket coverage of the hard scenarios: output, idle, active, detached and SIGTERM-ignoring leftovers, orphans after exit, `kill -9` restart cleanup with a reused pid, three run isolation, shutdown bound, and a log capture test.
